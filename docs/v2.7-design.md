## 1. Behind-skew clock detection — jam yang ketinggalan akhirnya ketahuan

### Masalah
Gate clock-skew v2.5 hanya menangkap arah AHEAD: timestamp lebih dari 15
menit di masa depan vs jam lokal adalah mustahil. Arah BEHIND tidak
tertangkap — jam yang 3 jam ketinggalan menulis timestamp yang terlihat
persis seperti klaim yang memang sudah kedaluwarsa. Baterai kasus langka
#3 mencatat ini sebagai "partial" dengan alasan "no signal in the record".

### Sinyal yang ternyata ada
Ada sinyal — bukan di dalam record klaim sendiri, tapi di relasinya dengan
git. Setiap klaim mencatat `base_commit` (HEAD saat klaim dibuat). Invarian
yang tidak bisa dilanggar:

> Waktu-riil pembuatan klaim R_c ≥ waktu-riil base commit R_B.
> Sebuah klaim tidak mungkin dibuat sebelum commit yang jadi base-nya ada.

Jadi kalau `started_at` klaim jauh SEBELUM timestamp base commit-nya, jam
penulis klaim pasti ketinggalan — dengan asumsi jam penulis base commit
waras. Perbandingan ini memakai dua jam yang berbeda (jam klaim vs jam
base), bukan satu jam melawan dirinya sendiri, jadi arah behind menjadi
terdeteksi.

### Desain
- Field baru **`created_base_commit`**: HEAD sha saat klaim dibuat, dicatat
  sekali di `cmd_claim`, **tidak pernah diubah** (renewal tidak menyentuhnya
  — renewal hanya meng-update `base_commit` kalau `--worktree` diberikan,
  karena worktree direbase ke base baru; `created_base_commit` tetap base
  pembuatan). Klaim lama (pre-v2.7) tidak punya field ini — gate memakai
  fallback `base_commit`, yang untuk klaim non-worktree memang tidak pernah
  di-renew sehingga IS base pembuatan. Klaim worktree lama yang pernah
  di-renew memakai `base_commit` hasil renew — sinyalnya melemah (base
  lebih baru dari pembuatan → gate lebih sensitif, bisa false-positive
  kalau renew-nya jauh setelah pembuatan; lihat "False positive" di bawah).
- Helper baru di `team_common.py`:
  - `git_commit_timestamp(repo_root, sha)` → aware datetime atau None.
    Memakai `git show -s --format=%cI <sha>` — **committer date**, bukan
    author date: committer date adalah saat objek commit itu ada, author
    date bisa jauh lebih tua (cherry-pick / rebase / commit dengan
    `GIT_AUTHOR_DATE` lama).
  - `check_claim_base_skew(claim, repo_root, grace_minutes)` → string
    error atau None. Skip (None) kalau: tidak ada base (klaim lama tanpa
    field, objek tidak dikenal, repo bukan git), timestamp base tidak bisa
    dibaca, atau `started_at` tidak bisa di-parse. FAIL kalau
    `started_at < base_ts − grace`.
- **Grace = `grace_minutes` (15) dari config** — sama dengan
  `CLOCK_SKEW_FAIL_MINUTES`. Tidak ada knob baru.
- **Tidak ada "now-guard".** Sengaja: kalau gate diam saat base_ts terlihat
  di masa depan vs jam validator, maka agent yang skew-nya sendirilah yang
  tidak bisa mendeteksi dirinya — hanya CI / agent lain yang bisa. Tanpa
  guard, hook pre-push agent yang skew itu sendiri gagal dengan pesan
  yang jelas, dan dia yang memperbaiki jamnya. Harga yang dibayar: satu
  false-positive tambahan (di bawah).
- **False positive yang jujur.** Kalau penulis base commit jamnya CEPAT
  lebih dari 15 menit, klaim yang waras terlihat "lahir sebelum base-nya"
  → false FAIL sementara. Pulih sendiri: release + re-claim setelah waktu
  berjalan melewati timestamp base (atau setelah jam base diperbaiki).
  Kasus yang sama muncul dari **history rewrite**: rebase yang menulis
  ulang base commit memberinya committer date baru, sehingga klaim lama
  yang berbasis commit itu terlihat ketinggalan — pulih dengan cara yang
  sama (release + re-claim, record segar dengan base baru). Pesan error
  menyebut base commit + kedua timestamp, supaya manusia bisa
  mendiagnosis mana dari dua jam itu yang salah — gate tidak mengklaim
  tahu jam siapa yang rusak, hanya bahwa keduanya tidak konsisten.
- **Wiring:** `claim.py cmd_check` (loop per-klaim, tepat setelah blok
  future-gate v2.5) dan `validate.py main()` (loop per-klaim, tempat yang
  sama). Dua tempat karena `validate.py` menduplikasi cek klaim secara
  inline dan tidak memanggil `cmd_check` — pola yang sama seperti gate
  v2.5.
- **Status-blind, seperti gate v2.5.** Gate berjalan untuk klaim dengan
  status apa pun — klaim yang sudah released/done dengan timestamp skew
  tetap FAIL sampai diperbaiki. Perbaikannya adalah release + re-claim
  **dengan task id yang sama**: claim baru menimpa record lama (record
  segar, `started_at` waktu-riil, `created_base_commit` baru), sementara
  jejak audit tetap ada di `events.jsonl`. Ini sengaja: record yang
  salah tidak boleh didiamkan menjadi sejarah yang lolos begitu saja.
  (Pengecualian yang disengaja ada di gate §2 — duplikat `created_seq`
  yang semuanya sudah released/done TIDAK di-FAIL, karena di sana
  tidak ada jalan perbaikan tanpa menulis ulang sejarah.)
- **Baterai kasus #3 diperbaiki, bukan dihapus.** Model "behind" lama
  tidak setia: ia hanya menggeser `expires_at`/`heartbeat_at` −3 jam,
  sementara `started_at` dibiarkan waktu-riil — padahal klaim dari agent
  yang jamnya ketinggalan 3 jam PASTI `started_at`-nya juga −3 jam.
  Baterai sekarang menggeser ketiganya, lalu menegaskan gate baru
  menangkapnya. Verdict #3 menjadi **CLOSED** (ordering + skew-ahead +
  skew-behind). Yang TIDAK berubah: klaim yang expired+stale tetap bisa
  diambil alih — gate membuat penyebabnya terlihat (FAIL di check), bukan
  melarang take-over-nya. Take-over klaim yang memang mati adalah perilaku
  yang benar; yang salah adalah diam-diam menganggapnya "cuma kedaluwarsa".

### Batas jujur (yang gate ini TIDAK lakukan)
- Hanya mendeteksi skew **saat klaim dibuat** vs base pembuatan. Jam yang
  waras saat klaim lalu ketinggalan belakangan (heartbeat meleset) tidak
  ditangkap gate ini — arah itu sudah ditangani staleness: heartbeat basi
  → klaim stealable (warning), bukan diam-diam hidup.
- Tidak membuktikan jam SIAPA yang salah — hanya inkonsistensi dua
  timestamp. Diagnosis tetap manusia.
- Klaim tanpa base yang bisa di-resolve (pre-v2.4, repo bukan git) di-skip,
  bukan di-FAIL — tidak ada sinyal, jadi tidak ada vonis.

## 2. created_seq ganda di bawah konkurensi sejati

### Masalah
`next_created_seq` = max atas SEMUA klaim + 1. Dua agent yang membaca max
yang sama secara bersamaan menulis seq yang sama. `next_created_seq`
sendiri mengakuinya ("A file cannot be an atomic counter") dan menyerahkan
ke "push fence + claim_seq + claim check on merge" — tapi tidak ada gate
yang benar-benar memeriksa duplikatnya. Dua klaim dengan `created_seq`
sama lolos check, dan urutan "siapa duluan" (yang dipakai semua aturan
konflik) menjadi tidak terdefinisi untuk pasangan itu.

### Desain
- Helper baru `team_common.find_duplicate_created_seq(claims)` →
  daftar (seq, [task_ids]) untuk seq > 0 yang dipakai ≥2 klaim berbeda.
  Seq ≤ 0 diabaikan: klaim pre-v2.4 tidak punya field ini.
- **FAIL hanya kalau ≥2 dari duplikat itu berstatus `active`.**
  Satu holder aktif + sisanya released/done tidak ambigu — yang
  released adalah sejarah mati: tidak bisa diperbaiki tanpa menulis
  ulang sejarah, dan tidak bersaing dengan siapa pun. Me-FAIL-kan
  satu holder aktif + sejarah mati hanya mem-brick push tanpa jalan
  keluar (pelajaran dari run pertama s12: setelah satu duplikat
  di-release, gate yang memakai ambang "≥1 aktif" tetap FAIL
  selamanya).
- Pesan error menyebut seq + task ids + perintah perbaikan: release
  duplikat aktif + re-claim (re-claim menghitung ulang max+1, jadi seq
  baru pasti unik selama tidak ada race baru).
- **Wiring:** `claim.py cmd_check` (cross-claim pass, dekat pass
  worktree-path) dan `validate.py` (tepat setelah blok double-claims
  file-conflict).
- **Batas jujur.** Gate ini MENDETEKSI, bukan MENCEGAH: race tetap bisa
  terjadi, dan yang menangkap adalah check/validate (pre-push + CI).
  Pencegahan atomik butuh server (atomic counter) — itu di §4, tetap
  kebuka. Docstring `next_created_seq` diperbarui: "push fence" sekarang
  bernama — gate duplikat ini.

## 3. Entry line citation — simbol harus ada DI baris yang dikutip

### Masalah
Entry registry `file:function` hanya membuktikan simbol itu ADA di file —
di mana saja. Klaim "fitur X ada di `src/auth/login.py:login`" tetap lolos
walau `login` yang dimaksud sudah pindah / yang ada di file itu fungsi
lain dengan nama sama di konteks berbeda / baris yang dikutip di dokumen
sudah tidak relevan. Ini lubang "fake-feature truth" dari arah lokasi:
registry bisa menunjuk ke tempat yang salah dan tetap hijau.

### Desain
- Format diperluas (opsional, backward-compatible):
  `file:function#line`, contoh `src/auth/login.py:login#14`. `#line`
  adalah **baris definisi** simbol itu.
- Helper `split_entry_line(entry)` → (base_entry, line atau None).
  Semua perbandingan duplikat memakai base entry — `x.py:f` dan
  `x.py:f#10` adalah simbol yang sama, bukan dua fitur.
- `check_symbol(path, symbol, line=None)` diperluas: kalau line diberikan,
  simbol harus DIDEFINISIKAN di baris itu persis (ast node `lineno`, atau
  regex fallback). Regex fallback juga diperbaiki: dulu hanya `def|class`,
  sekarang termasuk `async def` (sebelumnya `async def foo` lolos ast
  tapi gagal di regex fallback untuk file yang tidak bisa di-parse).
- `check_entry(entry, kind, repo_root)`:
  - `#line` ada tapi simbol tidak di baris itu → **FAIL**.
  - `#line` tidak ada (kind=code) → **WARN** "no line citation"
    (grandfather: entry lama tetap jalan, tidak di-FAIL).
  - Non-code kinds tidak berubah (entry = pointer, bukan `file:function`).
- `cmd_register` / `cmd_improve`: entry code yang BARU atau BERUBAH
  **WAJIB** bawa `#line` → FAIL kalau tidak. Entry yang tidak berubah
  (improve tanpa `--entry`) tidak dipaksa — grandfather tetap berlaku.
- `cmd_reverify`: TAMBAH line kalau kosong (cari simbol, update entry),
  UPDATE line kalau simbol pindah, FAIL kalau simbol hilang (sudah FAIL
  lewat `check_entry`). Pindah baris via reverify BUKAN contract change:
  kontrak = `file:function`, line hanya pointer.
- `cmd_check` (features): duplikat memakai base entry; WARN line-hilang
  muncul lewat `check_entry`.
- Starter repo diperbarui: `login-api` → `src/auth/login.py:login#14`,
  `price-monitor` → `scripts/monitor_harga.py:cek_harga#12`.
  `entry_blob_sha` tidak berubah (isi file tidak berubah).
- Dokumen: `SKILL.md` (contoh register + format entry) dan
  `references/feature-registry.md` (tabel format + § "Validasi entry
  point").

### Batas jujur (yang ini TIDAK lakukan)
- Ini memverifikasi kebenaran **LOKASI**, bukan kebenaran **DESKRIPSI**.
  Simbol yang ada di baris yang dikutip bisa saja tidak melakukan apa
  yang ditulis di `does` — itu tetap human-review. Registry yang jujur
  soal "di mana" masih bisa berbohong soal "ngapain" — dan skill ini
  tidak mengklaim sebaliknya.

## 4. Yang tetap kebuka (dan kenapa) — tidak dikerjakan di rilis ini

| Lubang | Kenapa tidak bisa ditutup di skill file+git |
|---|---|
| Live presence (siapa online sekarang) | Butuh server yang tahu siapa terhubung saat ini; file di git tidak punya "sekarang" yang live. |
| Atomic claims (klaim tanpa race sama sekali) | Butuh counter atomik / lock server-side; file tidak bisa jadi counter atomik (lihat §2 — yang bisa dilakukan file hanyalah mendeteksi race-nya). |
| Cross-repo board | Satu repo hanya melihat `team/`-nya sendiri; board lintas repo butuh server yang menggabungkan banyak repo. |
| Auto-merge / merge-decision automation | Keputusan merge mana yang menang butuh penilai (manusia / server); file hanya bisa mencatat keputusannya, bukan mengambilnya. |
| Semantic conflicts (dua perubahan yang merge bersih tapi maknanya tabrakan) | Butuh pemahaman arti kode — embeddings / model di server; diff teks tidak cukup. |
| No live supervision (tidak ada yang mengawasi agent saat bekerja) | File hanya dibaca saat check/push; tidak ada proses yang menonton di tengah jalan. |
| Fan-out ×N cost tanpa dedup | Biaya token fan-out adalah sifatnya (N agent = ×N token); dedup butuh server yang tahu hasil satu agent sebelum menjalankan yang lain. |
| Event-semantics replay | By design, shape only: `events.jsonl` mencatat bentuk event, bukan semantiknya — replay yang memaknai ulang event butuh interpreter di luar skill. |
| Worktree + branch terhapus barengan | Tidak ada bukti lokal: tidak bisa dibedakan dari "tidak pernah di-setup" atau "hidup di mesin lain". |
| Tes mesin kedua + git < 2.38 | Butuh hardware / environment kedua, bukan kode. |
| Receipt is a claim, not proof | Receipt menyatakan "selesai" — verifikasi bahwa pekerjaan itu benar tetap butuh pembacaan manusia / test; file tidak bisa membuktikan kebenaran isinya. |
| A gate is only as strong as the check before the push | Hook bisa di-bypass (`--no-verify`, clone tanpa hook); CI adalah gate sebenarnya — dan CI pun hanya sekuat branch protection yang dipasang manusia. |
| Signatures bind to a key, not a human | Tanda tangan membuktikan pemegang kunci, bukan identitas manusianya; itu batas kriptografi, bukan bug. |
