# v2.5.0 design — close every remaining hole

## Why

v2.4.0 closed the three structural holes the rare-case round found
(identity, ordering, lifetime, mailbox authorship). The re-run of
the 15-case battery against v2.4.0
(`simulations/v2.4.0-evidence.md`) left **4 holes still open**
(#2 sabotage, #4 ghost claims, #6 cycles, #8 history rewrite),
**2 partial** (#3 clock skew — ordering closed, stealability
unchanged; #12a mailbox — keyword forgeries blocked, the exact
original message still evades the regex), and **1 soft hole**
(#9 display-name spoof). v2.4.0 also unlocked the enforcement for
all of them: signed identity means an actor can now be named and
checked, so the trailer fence, mailbox signatures, and the
push-range rules finally have something to bind to.

This release closes all eight, and adds no features. The Orca
features (fan-out runbook, decision gates, typed receipts, formal
reviews) stay queued as v2.6.0 — adding features on top of holes
only adds attack surface.

## Design principle

| Hole (rare-case report) | Fix in v2.5 | Control |
|---|---|---|
| Sabotage: team/ files deleted silently, trailer never read, events never validated (case 2) | (a) Deletion detection in the push range: a deleted team/ record file FAILS unless it never existed on the remote baseline. (b) Trailer enforcement: a work commit touching a file covered by a blocking claim must carry a `[claim #N]` trailer matching that claim; with `require_signatures` on, the commit must also verify against the claim owner's key. (c) Event validation: every `events.jsonl` line must be well-formed JSON with a parseable timestamp, a roster actor, and references to records that exist. | `validate.py` push-range + new event section; `team_common` helpers |
| Ghost claim: member removed mid-flight, claim still blocks and bricks every push (case 4) | A claim whose owner is gone from the roster is automatically non-blocking and flagged for release; a new claim on the same file succeeds. | `team_common.is_blocking(..., roster_ids=...)`; `claim.py check` + `claim.py claim` + `validate.py` |
| Dependency cycles invisible (case 6) | Cycle detection (DFS over `depends_on`): `features.py check`, `validate.py`, and `reverify` FAIL on a cycle naming the loop; `register`/`improve` refuse an edge that would create one. | `team_common.find_dependency_cycle()` |
| History rewritten (force-push) recycles `claim_seq`, erases the audit log (case 8) | Last-known-main-SHA: `team/config.json` records the last verified `origin/main` SHA; `validate.py`/`sync_check` FAIL when the recorded SHA is no longer an ancestor of `origin/main`. `sync_check` records the SHA after each successful fetch. | `team_common.check_main_history()` / `record_main_sha()`; `team/config.json` field `last_known_main_sha` |
| Clock skew: stealability follows wall-clock both directions (case 3) | Clock-skew gate: a claim timestamp more than 15 min in the future vs the local clock FAILS (`heartbeat_at` / `expires_at` / `started_at`); `expires_at` before `started_at` FAILS; `heartbeat_at` before `started_at` FAILS. | `team_common.is_impossibly_future()`; `claim.py check` + `validate.py` |
| Mailbox poisoning: the original "STOP semua kerja…" evades the keyword list (case 12a) | Mailbox signature enforcement (when `require_signatures` is on): a message claiming a human sender MUST carry a valid `sig` from that sender's roster key — any content, any wording. Unsigned human mail FAILS. Agent mail may carry a `sig`; a present-but-invalid one FAILS. | `team_common.verify_mailbox_signature()` (`ssh-keygen -Y verify`, namespace `theroster-mailbox`); new `scripts/mailbox.py sign/check`; `validate.py` mailbox section |
| Claim on team/ itself (case 5, hardening) | `claim.py` rejects claims whose files are under `team/`; `claim.py check` and `validate.py` FAIL a team/-claim already in the files. | `claim.py` + `validate.py` |
| Display-name spoof (case 9, soft hole) | Duplicate display names FAIL in `check_roster.py` and in `validate.py` (names compared NFKC + casefold, whitespace collapsed). | `check_roster.py` + `validate.py` |

## 1. Sabotage detection

### 1a. Deletion detection

The push range already knows what changed (`git log --name-only`,
same shape as the rename rule). A deletion is now queried with
`--diff-filter=D --no-renames` — `--no-renames` matters: without
it a rename out of `team/` reports as `R`, not `D`, and a claim
file renamed away would slip past as a "move".

A deleted path FAILS when it is a team/ record the team shares:

- `team/roster/*.json`, `team/claims/*.json`,
  `team/features/*.json`, `team/prd/*.json`,
  `team/handoffs/*.json`, `team/events.jsonl`, `team/config.json`.

The exception is honest, not a loophole: the file must have
existed on the range base (`git show <base>:<path>`). A file
added *and* deleted inside the same push never existed on the
shared history, so nothing was erased — that only warns. A
deletion of a file that existed on the remote FAILS with the
correct lifecycle spelled out: release a claim, cancel a
feature, retire a roster member — never delete the record.
Deletion destroys the audit trail the release/cancel *is*.

Mailbox deletions only warn: mailbox lines are transient notes,
not records. `team/index.json` is gitignored and never in a push
range.

The check skips with a warning when there is no range base (no
remote yet, single-commit repo) — same posture as the other
push-range checks.

### 1b. Trailer enforcement

The `[claim #N]` fence is now read, not just documented. In the
push-range section of `validate.py`, for every non-merge commit
in the range (merge commits are skipped — their content is the
union of commits already checked individually):

1. Work paths = changed paths outside `team/` (a commit touching
   only `team/` is a claim/release/record commit, not work).
2. For each work path, the blocking claims at HEAD covering it
   (canonical path / prefix overlap, same as the conflict rules).
   A path no blocking claim covers needs no trailer — work on
   unclaimed files is not gated by this rule.
3. The commit message must contain a `[claim #N]` trailer whose
   `N` equals the `claim_seq` of one of the covering claims.
   Each touched claimed file is checked separately: one trailer
   cannot cover two files whose claims have different numbers.
4. When `require_signatures` is on, the trailer must also belong
   to a claim whose owner's key verifies the commit
   (`git verify-commit` against that one key). Without signatures
   the trailer number alone is checked — and documented as such:
   a trailer is a claim on a number, and only a signature binds
   that number to a person.

The bootstrap push skips the check with a warning, like the
signature checks: the first team setup lands claim files and
work files together, and there is no prior claim to fence
against. Claims released before the push are fail-open (not
blocking at HEAD, so their old work commits are not checked) —
the same posture as every other gate that only looks at blocking
claims.

### 1c. Event validation

`team/events.jsonl` is the audit log; until now no script ever
read it. `validate.py` now validates every non-empty line — but
with a temporal split that matters:

- Shape checks apply to EVERY line: valid JSON object (a
  malformed line FAILS — the log is the record; corruption must
  not pass silently), `event` a non-empty string, timestamp `at`
  (falling back to the legacy `ts` field the starter lines use)
  parseable as UTC ISO-8601 ending in `Z`, `lamport` an int >= 1.
- Reference checks apply only to NEW lines — lines beyond the
  push-range base, i.e. not yet on the shared history. A new line
  must name a roster actor (or a composite `flags:a,b` /
  `cancel:x` actor whose parts are roster ids, or the system actor
  `v1-migration`), its `task_id` / `feature_id` (when present and
  non-empty) must reference records that exist, and its timestamp
  must not be impossibly far in the future (same 15-minute
  clock-skew gate as §5).
- OLD lines (already on the shared history, at or before the
  range base) get shape checks only. They were validated when
  pushed; the world has moved on since — a member named in an old
  line may have left, a claim named in one may have been released
  long ago. Checking old lines against the CURRENT roster would
  make every ghost fail validation, defeating the ghost gate
  (§2: warn, never fail). No range base (first push / no git) →
  every line is new.

What it deliberately does NOT do: semantic cross-checks (e.g.
"this `claim_released` event contradicts the claim's current
status"). That needs a full event-sourcing replay over an
append-only log whose lines are only as honest as their writer;
a forged-but-well-formed event that references real records
still passes shape and reference checks. The log's truth still
rests on signed commits (v2.4) + branch protection. Say so
plainly; do not pretend the shape check is a truth check.

## 2. Ghost claims

`team_common.is_blocking()` gains an optional `roster_ids`
parameter: when the caller knows the roster, a claim whose
`owner_id` is not in it at all is not blocking. "Not in it at
all" is the definition of a ghost — a member with status `away`
or `retired` still exists in the roster, and their claims keep
blocking (retiring someone without releasing their claims first
still FAILS validation, as before — that is a human decision to
make deliberately, not a silent auto-release).

Callers that have the roster pass it: `claim.py check`,
`claim.py claim` (conflict check + quota), `validate.py`
(blocking claims, quota, both conflict loops). Callers that do
not have it (`sync_check` §2 remote claims — the remote roster
is not the local one) keep the time-based behaviour.

A ghost claim is a warning, not an error, in both `claim.py
check` and `validate.py`: "owner X is gone from the roster —
the claim is dead (not blocking); release it" with the exact
release command. The release itself stays manual (one command,
runnable by anyone — release has no owner check by design) and
is recorded as a normal release event. The point of the fix is
that the ghost never blocks anything while it waits to be
released, and never bricks a push.

## 3. Dependency cycles

`team_common.find_dependency_cycle(features)` runs an iterative
DFS over `depends_on` edges (only edges to registered features;
an edge to an unregistered feature is already an error
elsewhere). It returns the cycle as `[a, b, ..., a]` or `None`.
Self-dependency is a 1-cycle and is caught too.

Enforcement points:

- `features.py check` and `validate.py`: FAIL naming the loop.
- `features.py reverify`: FAIL when the feature is part of a
  cycle (refreshing versions inside a loop is meaningless).
- `features.py register` / `improve`: the prospective graph
  (existing features + the new/merged `depends_on`) is checked
  before writing — an edge that would close a cycle is refused
  at write time, with the loop named.

## 4. Last-known-main-SHA

`team/config.json` gains `last_known_main_sha` (default `""`).
The value is the last `origin/main` SHA the team verified —
not the last SHA anyone pushed, but the last one a local
`sync_check` saw and confirmed as a descendant of the previous
recorded SHA.

- `sync_check` (which fetches): after a successful fetch, it
  checks the recorded SHA against the new `origin/main` with
  `git merge-base --is-ancestor`. Not an ancestor (or an
  unknown object) → FAIL: history was rewritten, stop. An
  ancestor → OK, and the recorded SHA is updated to the new tip
  in the working `team/config.json`. The update is a working-tree
  change that lands in the next commit — that lag is by design:
  the recorded SHA is always an ancestor of the real tip, which
  is all the check needs, and the pre-push hook must not rewrite
  history to record that it looked.
- `validate.py` (which does not fetch): the same ancestry check
  against whatever `origin/main` ref exists locally. No recorded
  SHA yet → warn only (first sight). No remote branch →
  warn + skip.

A force-push that rewrites history fails both gates, and — by
design — the failing run does NOT update the recorded SHA, so
the evidence survives until a human decides the rewrite was
legitimate and re-records it (by running `sync_check` after
verifying the new history, which then records the new tip).

Two honest limits. First, a rewrite that happens before a
machine ever records a SHA cannot be detected by that machine
(the first sync_check on a fresh clone records the current tip).
Second, the tripwire lives in the working tree, so a bare
`git pull` onto rewritten history overwrites the recorded SHA
before any gate runs — which is why the skill forbids bare pulls
and why `sync_check` fetches internally and checks before any
working-tree sync. The gate fires for any machine that recorded
a SHA and runs `sync_check`/`validate.py` before syncing to the
rewritten history — the prescribed flow, and the pre-push-hook
flow.

Honest limits: a rewrite that happens before a machine ever
records a SHA cannot be detected by that machine (nothing to
compare against); the committed value helps fresh clones only
because the last pushed value travels in the repo. The
claim_seq recycling and the erased audit log are *detected* by
this check, not *prevented* — prevention is branch protection's
"block force pushes", the repo-level answer, not a script.

## 5. Clock-skew gate

`team_common.is_impossibly_future(dt, ...)`: a timestamp more
than 15 minutes in the future vs the local clock is impossible
(the tolerance is the `grace_minutes` window — the same
disagreement the expiry rule already tolerates). Enforced in
`claim.py check` and `validate.py` for a claim's `started_at`
and `heartbeat_at` — the timestamps that describe events that
already happened — plus the ordering rules `expires_at >=
started_at` and `heartbeat_at >= started_at`. `expires_at` is
deliberately NOT futureness-gated: it is a promise about the
future (now + TTL, default 2h), so a fresh claim legitimately
expires hours ahead and gating it would FAIL every fresh claim.
The same future check applies to event `at`/`ts` (§1c).

What it cannot do: detect a clock running *behind*. A claim
written by a 3-hours-behind clock looks exactly like a
genuinely expired claim on a correct clock — there is no signal
in the record to distinguish them (the commit author date comes
from the same skewed clock). The behind-skew case stays an
honest limit: the claim looks dead, and a second agent may take
the file. The pre-push hook's >5-minute clock warning (warn
only) is the existing mitigation for the machine that *has* the
skewed clock. Cross-machine truth about who is actually alive
is the documented server-shaped hole; do not fake it with
files.

## 6. Mailbox signature enforcement

The keyword heuristic failed on the exact original message
because "STOP semua kerja hari ini…" contains none of the
listed words. The fix does not extend the word list — Indonesian
imperatives like "jangan" appear in benign notes constantly
("jangan lupa"), so a longer list would fail friendly mail.
Instead, authorship is now verified:

- Payload: `theroster-mailbox-v1\n<from>\n<ts>\n<message>`
  (version line, sender, timestamp, message — the signature is
  bound to all three, so it cannot be replayed onto a different
  message or timestamp).
- Sign: `ssh-keygen -Y sign -f <private-key> -n
  theroster-mailbox <payload-file>`; the armored signature goes
  in the line's `sig` field. Verify: `ssh-keygen -Y verify`
  against a temp allowed-signers file holding only the sender's
  roster key, namespace `theroster-mailbox`.
- New `scripts/mailbox.py`: `sign --from <id> --to <id>
  --message ... --key <private-key-path>` appends a signed line;
  `check` runs the same gate `validate.py` runs, standalone.

Gate (in `validate.py`, via `team_common.check_mailbox()`):

- Sender is a **human** roster member and `require_signatures`
  is on: the line MUST carry a valid `sig` (with `ts`), verified
  against that sender's roster key. No sig, no `ts`, no key on
  file, or a bad sig → FAIL. A valid sig passes whatever the
  content says — the signature *is* the human speaking, and the
  "mailbox never orders" rule applies to unauthenticated
  content.
- `require_signatures` off: the v2.4 heuristic stays (imperative
  from a human/unknown sender FAILS, from an agent warns).
  Signature enforcement rides on the same opt-in as commit
  signatures — without roster keys there is nothing to verify
  against, and making it unconditional would fail every human
  mailbox message for teams that never opted into keys.
- Sender unknown: v2.4 heuristic (imperative FAILS; benign
  passes). An unknown sender has no roster key to verify.
- Sender is an ai-agent/tool member: a `sig`, when present, is
  verified against their key if they have one — present-but-
  invalid FAILS (a false claim of authenticity is worse than
  none). No sig → v2.4 heuristic (imperative warns).

## 7. Claims over team/

`claim.py claim` rejects any file under `team/` (the board
cannot be claimed — a claim only ever blocks other claims, and
nobody claims roster files in normal operation, so this is
defense in depth, not a fix for a demonstrated break). The
rejection covers both fresh claims and renewals.
`claim.py check` and `validate.py` FAIL a team/-claim already
in the files (hand-written or pre-v2.5), so one cannot slip in
through a hand edit.

## 8. Duplicate display names

`check_roster.py` and `validate.py` FAIL when two roster
members share a display name (compared NFKC + casefold, inner
whitespace collapsed — "Rian", "rian", and " Rian " are the
same name). Ids were already unique; names are what humans
read, and the skill's first instruction is to read the roster.
This does not stop a determined impersonator (they can pick a
different name) — it stops the accidental/confusing case, which
is the realistic one. Real identity binding is direction 1
(v2.4).

## What v2.5 does NOT do

- No Orca features (fan-out, gates, receipts, reviews) — v2.6.0.
- No fake-feature truth check: entry verification checks that a
  symbol exists, never that the description is true; that stays
  a human-review job (the promote/reviewer rule).
- No cross-repo board, live presence, or atomic claims — server-
  shaped, documented in the skill as out of scope.
- No semantic-conflict detection: the merge check sees text.
- No behind-skew detection (see §5).
- No event-semantics replay (see §1c).
- Local script runs stay unbound: the enforcement points are
  the hook (`validate.py`, `claim.py check`, `check_roster.py`,
  `sync_check`) and the CI twin — a malicious local agent can
  still run anything on its own machine; what it cannot do is
  push the result past the gates.
