# v2.3.0 design — worktree-per-claim mode

## Why

v2.0–v2.2 solved "who is doing what" with claims. But claims only
*fence* a file: two agents may still not touch the same file at the
same time, even when the work is genuinely parallel and the merge
would be trivial. In a shared checkout that fence is necessary —
whoever edits second overwrites the first on disk.

A git worktree removes the shared floor. Each agent gets its own
checkout of the repo, on its own branch, on its own disk path. Two
agents can edit the *same file* at the same time and never see each
other's bytes. The merge, not the filesystem, becomes the collision
point — and a merge can be checked mechanically before it lands.

This is the mode Orca (Stably AI) made popular: one worktree per
task, compare diffs, merge the best. TheRoster's version is smaller
and cheaper: no desktop app, no server, no orchestration layer.
Just a claim that records *where* the work happens, a merge check
that replaces the overlap check, and one hard rule that keeps the
claim board honest.

## The Dziatkovskii rule — the one rule that matters

Anton Dziatkovskii ran 94 worktrees in November 2026 and lost track
of 43 branches with committed work. His post-mortem names the cause
precisely: *"the board file had only one commit in its history since
September 30, despite agents using it. The manual step was skipped,
and the file lived in the repository, meaning each worktree had its
own isolated, empty version of the board."*

A coordination file that lives inside the repo does not coordinate
across worktrees unless it is pushed to a shared branch immediately
and continuously. So v2.3 enforces:

> **The claim itself is pushed to `main` first, alone, before any
> work starts in the worktree. All reads of `team/` state come from
> the main checkout or from `origin` — never from inside a worktree.
> Any script that mutates `team/` state refuses to run from inside a
> linked worktree.**

If a worktree is never merged, its claim is still visible on `main`,
its branch is still named in the claim, and a human can find the
work. An orphaned worktree is a recoverable branch, not a lost
branch.

## Design principle

| Shortcoming of claims in a shared checkout | Mitigation in v2.3 | Control |
|---|---|---|
| Two agents cannot edit the same file at once, even when the edits don't overlap | Worktree-per-claim: each claim names its own worktree + branch; overlapping file claims are allowed **only** between two worktree claims on *different* worktrees | `claim.py` conflict check exempts worktree-vs-worktree pairs with different paths; any pair involving a shared-checkout claim still conflicts |
| The claim board can go invisible inside a worktree (Dziatkovskii trap) | The claim is pushed alone to `main` first; reads of `team/` state resolve to the main checkout; mutations from inside a worktree are refused | `team_common.resolve_team_dir()` / `guard_team_mutation()`; `claim.py`, `features.py`, `prd.py` all call the guard |
| A merge conflict is discovered only at merge time, by a human | `sync_check` in worktree mode becomes a merge check: it verifies the worktree branch merges cleanly onto `origin/main` and fails on conflict | `sync_check.py --mode worktree` (auto when the claim is a worktree claim); `git merge-tree --write-tree` (git ≥ 2.38), trial-merge fallback |
| A worktree branched from an old base silently misses new work | Stale-copy rule: a worktree whose base is more than `branch_freshness_commits` (20) behind `origin/main` must rebase before its push is accepted | `sync_check` merge mode fails past the limit; `validate.py` fails a worktree claim whose base_commit is unknown to the repo |
| A fresh worktree is an empty room: no `node_modules`, no `.env`, no cache | Shared-paths convention: symlink `node_modules` / `.cache` from the main checkout (only if gitignored there); copy `.env` files (never symlink — a symlink would make the worktree's env edits land on main's disk) | `scripts/worktree_setup.sh`; keys `worktree_shared_dirs` / `worktree_copy_files` in `team/config.json` |
| A worktree claim that points nowhere (deleted path, renamed branch) looks alive | `validate.py` / `doctor.py` check worktree claims for consistency: worktree path exists on this machine or is clearly marked remote-only, branch matches the worktree list, base_commit is a known commit | `validate.py` worktree section; `doctor.py` worktree checks (git ≥ 2.38 warning, setup script presence) |

## The flow

```
main checkout                    worktree (per claim)
─────────────                    ───────────────────
1. claim --worktree ../wt-a
   --branch wt/t-201
   → team/claims/t-201.json
     { worktree, branch, base_commit }
2. git add + commit + push
   the claim file ALONE
   → visible to everyone on main
3. worktree_setup.sh ../wt-a
   wt/t-201 <base_commit>
   → git worktree add + shared paths
4. work inside ../wt-a
   (same file as another agent? fine —
    they are on a different worktree)
5. sync_check merge mode
   → rebase onto origin/main if stale
   → FAIL on merge conflict
6. push branch, open PR, merge
7. git worktree remove ../wt-a
   (after the merge — never before)
```

## Config

```json
{
  "worktree_mode": "off",
  "worktree_shared_dirs": ["node_modules", ".cache"],
  "worktree_copy_files": [".env", ".env.local"]
}
```

`worktree_mode` is `"off"` by default — v2.3 changes nothing for
teams that don't opt in. `"per-claim"` enables `--worktree` on
`claim.py` and the merge mode of `sync_check.py`. There is no
`"always"` mode: a claim is either a worktree claim or a
shared-checkout claim, and mixing the two on the same file is
refused (see below).

## Rules

- **One claim = one worktree = one branch.** A worktree claim
  records `worktree` (path, repo-relative or absolute), `branch`,
  and `base_commit` (the `origin/main` head at claim time).
- **The claim is pushed alone first.** Same rule as v2.0, now with
  a sharper reason: if the claim never reaches `main`, the worktree
  is invisible and the Dziatkovskii trap opens.
- **Same file, different worktrees: allowed.** Two worktree claims
  may cover the same file only when their worktree paths differ.
  The merge check, not the claim check, decides whether the two
  edits land cleanly.
- **Same file, mixed modes: refused.** A worktree claim overlapping
  a shared-checkout claim (or vice versa) is a conflict. The
  shared-checkout agent's files live on the main disk; letting a
  worktree branch from under it reintroduces the race the claim
  system exists to prevent.
- **Same worktree path, two claims: refused.** Two claims naming
  the same worktree path share a checkout, so the normal overlap
  rule applies.
- **The worktree path must be outside the repo.** A worktree nested
  inside the main checkout pollutes the main tree and confuses
  `git status`. `claim.py` refuses paths inside the repo root.
- **The branch must not exist yet.** A worktree claim creates a
  fresh branch. Resuming work in an existing worktree is out of
  scope for v2.3 — open a new claim.
- **Stale means rebase.** More than `branch_freshness_commits`
  (20) behind `origin/main` → `sync_check` fails with "rebase
  first". More than 2× the limit, or a base_commit the repo has
  never seen → `validate.py` fails the claim.
- **Merge mode replaces the overlap check.** In worktree mode
  `sync_check` does not check for overlapping claims on the same
  files — that check is meaningless across isolated checkouts. It
  checks: worktree exists on this machine, branch matches,
  base known, not stale, merge onto `origin/main` is clean.
  When the worktree lives on another machine, the merge check is
  skipped with a note (the merge is then the PR's job, not the
  script's).
- **Remove the worktree after the merge.** A merged worktree left
  behind is the next Dziatkovskii incident in miniature.
  `git worktree remove <path>` (or `git worktree remove --force`
  after confirming the branch is merged — never `--force` on
  unmerged work).
- **Never symlink `.env`.** Copy it. A symlink means the worktree
  and the main checkout share one secrets file; an edit in either
  place lands in both.
- **Never write `team/` state from inside a worktree.** The scripts
  refuse. If you are standing in a worktree and need to claim,
  heartbeat, register, or cancel — `cd` to the main checkout
  first.

## What it does NOT fix

- **Semantic conflicts.** Two worktrees can both merge cleanly and
  still break each other (renamed function here, new caller there).
  The merge check is textual. Review the diff, as always.
- **Orphaned worktrees.** The skill cannot delete a worktree on a
  machine it cannot see. The claim on `main` names the branch and
  the worktree path, so a human can always find and clean up — but
  the cleanup itself is manual.
- **Cross-machine truth.** A worktree claim is visible on `main`,
  but whether the worktree still exists on its machine is only
  knowable on that machine. `validate.py` warns (not fails) when a
  worktree path is absent locally — the claim may simply live on a
  teammate's laptop.
- **Live presence.** Same honest limit as before: visibility is
  bounded by fetch / push. A worktree claim tells you where the
  work *should* be, not that someone is typing there right now.
- **Fan-out.** Running the same task in N worktrees and picking the
  best diff is a separate feature (`fanout_group`, planned after
  v2.3). v2.3 gives it the primitives — worktree claims + merge
  checks — but no runbook and no grouping field yet.
