# v2.6.0 design — Orca features (fan-out, decision gates, receipts, reviews)

## Why

v2.5.0 closed every hole the rare-case round left open, and the
hardening is what makes this release possible: every feature here
needs an actor that can be named and checked, and signed identity
(v2.4) + the v2.5 gates provide exactly that. The Orca research
(`~/workspace/research_notes/orca-vs-theroster-20261115/report.md`)
ranked four Orca patterns as file-able and worth stealing — this
release builds all four, as patterns, not as Orca's app:

| Orca pattern | TheRoster v2.6.0 | Control |
|---|---|---|
| Fan one prompt across N agents, compare diffs, merge the winner (§6.2) | `team/fanout/<id>.json` + `scripts/fanout.py` (create/add/compare/decide/cancel/check) + `fanout_group` on claims. Opt-in, explicit, N ≤ 8. | `fanout.py` + `claim.py --fanout-group` + `validate.py` |
| Explicit decision gates (§6.3) | `team/gates/<id>.json` + `scripts/gates.py` (create/list/resolve/waive/check). A claim bound to an open gate is refused at claim time and FAILs at push time — the same enforcement shape as a cancelled feature. | `gates.py` + `claim.py` + `validate.py` + `prd.py` done-gate |
| Typed completion receipts, `worker_done` (§6.4) | `team/receipts/<task-id>.json`, filed by `claim.py done` — no silent done. Bound to `claim_seq` (TheRoster's `dispatchId`), outcome required, even on failure. | `claim.py done` + `scripts/receipts.py` (list/check/show) + `validate.py` |
| Formal review record (§6.5) | `team/reviews/<id>.json` + `scripts/reviews.py` (create/list/check). Reviewer ≠ subject owner (same rule as stable promotion). A latest `request-changes` review blocks the PRD done-gate. | `reviews.py` + `prd.py` + `validate.py` |

What is deliberately NOT copied: live presence / 5-minute
heartbeats (needs a server — the premium ladder, not a file
tweak), fan-out by default (5× tokens), a merge queue, Orca's
app, Orca's command names (its orchestration CLI is experimental
and its flags shift).

## Design principles

1. **Sharded + index + event log, like everything else.**
   Each new record type is one file per record under `team/`,
   listed in the generated `team/index.json`, and every mutation
   bumps `lamport` (+1) and appends one line to
   `team/events.jsonl`. No new concepts for the team to learn
   beyond the four record types.
2. **The claim file is the source of truth for member status.**
   A fan-out group's `members` list is an append-only roster
   (task, owner, branch, worktree, added_at) — it does NOT cache
   a copy of each member claim's status. `fanout.py compare` and
   `list` read each member claim's live status + receipt. A
   cached copy would go stale the moment a member is released
   directly, and a stale scorecard is worse than none.
3. **Enforcement rides on v2.4/v2.5, it is not re-invented.**
   New records are covered by the same push-range rules as the
   old ones (ownership, signatures, deletion detection — see §6),
   by the mailbox trust model where they touch the mailbox
   (review delivery), and by the clock-skew gate on their
   timestamps.
4. **A record that cannot be attributed is not a record.**
   Every new record names a roster member as its actor
   (created_by / done_by / reviewer / decided_by). A forged
   receipt or review fails the same way a forged claim does:
   the referenced claim must exist, the `claim_seq` must match,
   and the actor must be the claim's owner (or a human).

## 1. Fan-out runbook + `fanout_group`

### The cost, first

Fan-out costs ×N tokens (Orca's own hands-on test: five agents
means five times the consumption, ~2 GB RAM per live agent, disk
×N worktrees). The runbook in SKILL.md names the cost before the
benefit, and the rules are:

- **Use it only for high-uncertainty work**: a bug with several
  valid fixes, a refactor with several defensible architectures.
  Never as a default. Never for routine work, never for anything
  with one right answer, never when the registry already has a
  stable feature (search first — the registry is still the
  counterweight to rebuilding the same thing N times).
- **N is 2–8, default 5** (`--max-members` at create; Orca's
  canonical five). One member is not a fan-out — `create` with
  `--max-members 1` FAILS.
- **Same-file members REQUIRE worktree mode.** Two sibling
  claims on the same file in a shared checkout conflict by the
  existing rule (a shared-checkout claim always shares the main
  checkout — `claims_share_checkout`), so the second sibling is
  refused at claim time. That is not a special case: it is the
  v2.3 rule doing its job. The runbook says: turn on
  `worktree_mode: "per-claim"` first, give each member its own
  worktree (`--worktree`), and merge the winner's branch via PR.
  Members on *different* files need no worktree.
- **The decider is not the winner.** `fanout.py decide --by X`
  requires X to be an active roster member AND X must not be the
  owner of the winning claim — nobody picks their own work as
  the winner. (A loser conceding to a winner is fine.)
- **Decide only when every member is settled.** A member still
  `active` without a receipt blocks the decision — wait for it,
  release it, or stall it first. A member that is `done` (receipt
  filed) or `released` is settled. The winner must be settled
  too, and if its receipt says `failed` it cannot be the winner.

### Record: `team/fanout/<id>.json`

```json
{
  "id": "t-101",
  "title": "Fix the checkout race",
  "prompt": "Fix the race in src/checkout.py; keep the public API.",
  "status": "open",
  "max_members": 5,
  "members": [
    {"task_id": "t-101-a", "owner_id": "assistant", "branch": "wt/t-101-a",
     "worktree": "../wt-t-101-a", "added_at": "2026-11-15T10:00:00Z"}
  ],
  "winner_task_id": "",
  "decided_by": "",
  "decided_at": "",
  "decision_reason": "",
  "cancelled_by": "",
  "cancel_reason": "",
  "created_by": "owner",
  "created_at": "2026-11-15T10:00:00Z",
  "lamport": 1
}
```

Statuses: `open → decided`, `open → cancelled`. Both terminal —
a decided group is not re-opened; a new attempt gets a new group.

### Commands: `scripts/fanout.py`

- `create --id --title --prompt --by [--max-members 5]` —
  creates the group (`open`). `--by` must be an active roster
  member. Warns (not fails) when `worktree_mode` is off: same-file
  members will not be claimable until it is on.
- `add --id --task --title --owner --files ... [--branch] [--worktree] [--claims-dir]`
  — the canonical way to add a member: it runs the claim path
  (same validation as `claim.py claim`, plus `--fanout-group`)
  and appends the member entry to the group record in the same
  call. It is a thin wrapper over `claim.py claim
  --fanout-group <id>` — one code path for both entry points, so
  a claim created directly with `--fanout-group` and one created
  via `add` are indistinguishable.
- `compare --id` — the scorecard, not a merge tool. For each
  member, one line: task, owner, live claim status, receipt
  outcome + summary + files modified (or "no receipt yet"), and
  the branch diffstat vs the claim's `base_commit` when the
  branch exists on this machine ("branch not on this machine"
  otherwise — the diff is then the PR's job, not the script's).
  Exit 0 always (it reports; it does not judge).
- `decide --id --winner <task-id> --by --reason` — records the
  winner, releases every other member claim in the same call
  (`released_by: "fanout:<winner>"`, one `claim_released` event
  per loser — the same shape as feature cancellation), sets the
  group `decided`. Refuses: unknown winner, winner not a member,
  winner's receipt `failed`, any member still active without a
  receipt, decider is the winner's owner, group not `open`.
  **Signature attribution:** `released_by: "fanout:<winner>"` is
  a composite actor (like `flags:` / `cancel:`) — the signature
  check skips it, and the decide commit is bound to the decider
  through the group record's `decided_by` in the same commit.
  Without the skip, the check would try to verify the commit
  against a non-person (`fanout:t-101-a`) and fail every decide.
- `cancel --id --by --reason` — releases every ACTIVE member
  claim (`released_by: "fanout-cancel:<by>"`, also a composite
  actor, skipped the same way) and sets the group `cancelled`.
  Any active roster member may cancel (same posture as feature
  cancellation).
- `list`, `check [--roster]` — `check` validates: id grammar,
  required fields, status values, `max_members` 2–8, members
  reference existing claims, no duplicate task ids, a decided
  group names a member as winner, a decided group's loser claims
  are released (a decided group with a still-active loser is an
  unfinished decision — FAIL, not warn).

### Enforcement in `claim.py` / `validate.py`

- `claim.py claim --fanout-group <id>`: the group must exist
  and be `open`; member count must be below `max_members`; the
  claim records `fanout_group`. (The conflict rule is unchanged:
  same-file siblings need different worktrees.)
- `claim.py check` / `validate.py`: a claim naming a group that
  does not exist FAILS; a claim naming a group it is not listed
  in FAILS (hand-written membership is not membership).
- `validate.py` (fan-out section): the same checks as
  `fanout.py check`, plus the decided-loser rule.

## 2. Decision gates `team/gates/`

### What a gate is

A gate is a named question that blocks work until it is answered
— the file-based version of Orca's `gate-create` /
`gate-resolve`. Today "wait for a decision" in TheRoster is an
informal mailbox message: no record that a task is blocked on a
named question, no list of open gates, and no enforcement. A
gate makes the block explicit, owned, and auditable in git.

### Record: `team/gates/<id>.json`

```json
{
  "id": "g-001",
  "question": "Merge the winner, or keep both implementations?",
  "options": ["merge-winner", "keep-both"],
  "blocks_kind": "prd",
  "blocks_id": "prd-003",
  "status": "open",
  "resolution": "",
  "resolved_by": "",
  "resolved_at": "",
  "resolved_by_review": "",
  "waived_by": "",
  "waived_at": "",
  "waive_reason": "",
  "created_by": "owner",
  "created_at": "2026-11-15T10:00:00Z",
  "lamport": 1
}
```

- `blocks_kind` is `claim` (one task id), `prd` (one PRD item),
  or `feature` (one feature id). Exactly one subject.
- `options` may be empty — then the resolution is free-form
  text. When non-empty, the resolution MUST be one of the
  options.
- Statuses: `open → resolved`, `open → waived`. Both terminal.
  A resolved gate is not re-opened; a new question gets a new
  gate.

### Commands: `scripts/gates.py`

- `create --id --question [--options ...] --blocks-kind {claim|prd|feature} --blocks-id <id> --by` —
  `--by` must be an active roster member; the blocked subject
  must exist (a claim / PRD item / feature with that id).
- `list [--status open]`, `check [--roster]`.
- `resolve --id --resolution <text> --by [--review <review-id>]` —
  `--by` must be an active roster member AND must differ from the
  subject's owner (the worker cannot resolve their own blocker —
  the same rule as stable promotion's reviewer). For a `claim`
  subject that does not exist yet, there is no owner to differ
  from, so any active member may resolve (the gate was created by
  the coordinator before the claim exists; the constraint bites
  once the claim exists and has an owner). `--review` cites the
  review that justifies the resolution: it must exist, target
  the same subject, and its verdict must be `approve` — a
  `request-changes` review cannot satisfy a gate. The gate
  records `resolved_by_review`.
- `waive --id --by --reason` — waiving is a human act: `--by`
  must be a roster member of type `human`. (An agent waiving its
  own blocker is meaningless — the gate exists to force a human
  decision. A human waiving is still recorded: who, when, why.)

### Enforcement — refuse at claim time, FAIL at push time

The same shape as a cancelled feature (Orca report §6.3):

- **Claim time (`claim.py claim`):** a new claim bound to an
  open gate is REFUSED. Binding:
  - gate on a `claim` → the claim with that task id;
  - gate on a `prd` → any claim with `--prd <id>`;
  - gate on a `feature` → a claim with `--reserves-feature <id>`
    OR whose files overlap the feature's registered files.
- **Check time (`claim.py check`, `validate.py`):** a BLOCKING
  claim bound to an open gate FAILS. This is the mid-work case:
  a gate created after the claim exists stops the worker at the
  next check / push — it does not freeze them mid-keystroke
  (same honest limit as cancellation: visibility is bounded by
  fetch/sync_check, not eliminated).
- **PRD done-gate (`prd.py status --to done`, `validate.py`):**
  an item with an open gate on it cannot be marked `done`.
  A gate on a feature of the item blocks it too.

`sync_check.py` is deliberately untouched: gates are local
records, and after fetch + rebase they are in the local tree —
`validate.py` reads them there. Sync is about remote state;
gates are enforced where the work is claimed and pushed.

## 3. Typed completion receipts

### What a receipt is

Orca's worker contract, file-based: `worker_done` exactly once,
even on failure, with outcome + summary + files modified, bound
to (task, dispatch) so a stale retry cannot complete the wrong
attempt. TheRoster's analogue of `dispatchId` is `claim_seq` —
the attempt identity the trailer fence already uses.

### Record: `team/receipts/<task-id>.json`

```json
{
  "task_id": "t-101-a",
  "claim_seq": 3,
  "outcome": "succeeded",
  "summary": "Fixed the race; added a regression test.",
  "files_modified": ["src/checkout.py", "tests/test_checkout.py"],
  "follow_ups": ["t-102: migrate the old callers"],
  "done_by": "assistant",
  "done_at": "2026-11-15T10:30:00Z",
  "sig": "",
  "lamport": 1
}
```

One file per task id. A re-claim of the same task (new
`claim_seq`) overwrites the receipt — the old attempt's receipt
survives in `team/events.jsonl` (`receipt_filed` events are
append-only), so history is not lost, it is just not in the
record file. The latest receipt is the current truth.

### Filing: `claim.py done` — no silent done

`claim.py done` now REQUIRES a receipt:

```bash
python3 claim.py done --task t-101-a --by assistant \
    --outcome succeeded --summary "Fixed the race; added a regression test." \
    --files-modified src/checkout.py tests/test_checkout.py \
    [--follow-ups "t-102: migrate the old callers"] [--key ~/.ssh/id_ed25519]
```

- `--outcome` is `succeeded|failed`, `--summary` is required,
  `--by` is required. Missing any of them FAILS with the exact
  flags to add. (No existing scenario used `claim.py done` —
  they all used `release` — so nothing in the suite depends on
  the old silent form.)
- The claim must exist and be `active`; `--by` must be the claim
  owner, or a human roster member filing on the worker's behalf.
- The receipt's `claim_seq` is the live claim's `claim_seq` —
  a receipt filed against a stale/released claim is rejected
  (the anti-stale-retry property: a retry cannot complete the
  wrong attempt).
- `files_modified` entries must be syntactically valid exact
  file paths. They are NOT restricted to the claim's files: work
  creates new files, and a new file inside a claimed directory
  is unclaimed until claimed — the receipt names what changed,
  the claim names what was fenced.
- **A `failed` outcome still marks the claim `done`** — the
  attempt is over. What it does NOT do is mark the work done:
  the PRD item stays `in_progress` and the feature stays
  `experimental`, because the feature's stability gate
  (`validate.py`: a done item's features must be stable) already
  refuses a done item built on unfinished work. No new gate is
  needed for that; the receipt makes the failure visible instead
  of silent.
- **Signing.** When `require_signatures` is on and `done_by` is
  a HUMAN roster member, the receipt MUST carry a valid `sig`
  (`--key` is required): payload
  `theroster-receipt-v1\n<done_by>\n<done_at>\n<task_id>\n<claim_seq>\n<outcome>\n<summary>`,
  namespace `theroster-receipt`, `ssh-keygen -Y sign/verify`
  against the sender's roster key — the same shape as the
  mailbox scheme (`team_common.verify_receipt_signature()`).
  The signature is verified against the roster key BEFORE the
  receipt is written (like `mailbox.py sign`). An ai-agent
  `done_by` needs no sig: the receipt file lands in a commit,
  and the commit signature binds it when `require_signatures`
  is on. A `--key` given for an agent signs too, when the agent
  has a key on file.
- The command writes the receipt AND flips the claim to `done`
  in one call, appending `claim_done` + `receipt_filed` events.
- **Push-range attribution (`done_by` on the claim).** The claim
  record gains a `done_by` field, set by `cmd_done` to the filer.
  `validate.py` attributes a done claim to its *filer*, not its
  owner — the same shape as `released_by`/`stalled_by` — in both
  the one-owner rule and the signature check. Without this, a
  human filing a receipt on an agent's behalf could never push:
  the claim file (owner = the agent) and the receipt file
  (`done_by` = the human) in one commit would fail the one-owner
  rule, and no single key could sign both records. With it, the
  commit has one actor (the filer) and one key. A pre-v2.6 done
  claim has no `done_by` and is attributed to its owner, as
  before.

### Verification (forgery detection): `receipts.py check` + `validate.py`

- The referenced claim must exist; `claim_seq` must match the
  claim's; `done_by` must be the claim owner (or a human);
  `outcome` must be `succeeded|failed`; `summary` non-empty;
  `done_at` parseable UTC-Z; `lamport` ≥ 1.
- With `require_signatures` on and a human `done_by`: a missing
  or invalid `sig` FAILS. Without it: a present-but-invalid `sig`
  FAILS (same posture as mailbox agent lines).
- What this does NOT do: verify the summary is true. A receipt
  that says "succeeded" for work that does not work is caught by
  the review (a human or a second agent reads the diff), not by
  the receipt — the receipt is the claim of completion, the
  review is the check of it. Say so plainly.

## 4. Formal review record `team/reviews/`

### What a review is

Orca's best UX is Annotate AI Diff: comment on an exact line,
the agent gets focused feedback. TheRoster has no UI and will
not pretend to build one — but the *record* is file-able: who
reviewed, what verdict, which lines, what the worker must fix.
The merge decision is currently an act with no artifact; this
makes it one.

### Record: `team/reviews/<id>.json`

```json
{
  "id": "r-001",
  "task_id": "t-101-a",
  "prd_item": "",
  "feature_id": "",
  "reviewer": "teammate-1",
  "verdict": "request-changes",
  "note": "The race is fixed, but the test does not cover the timeout path.",
  "annotations": [
    {"file": "src/checkout.py", "line": 42, "note": "timeout still unhandled here"}
  ],
  "created_at": "2026-11-15T11:00:00Z",
  "lamport": 1
}
```

Exactly one target (`task_id` / `prd_item` / `feature_id`).
`verdict` is `approve` or `request-changes`.

### Commands: `scripts/reviews.py`

- `create --id --task <id> | --prd <id> | --feature <id> --reviewer <id> --verdict {approve|request-changes} --note "..." [--annotation <file>:<line>:<note> ...] [--key <private-key>]` —
  the reviewer must be an active roster member AND must differ
  from the subject's owner (claim owner / PRD owner / feature
  owner — the same rule as stable promotion: nobody reviews
  their own work). The target must exist. Annotations: valid
  file path, positive line number, non-empty note.
- `list`, `check [--roster]`.

### Delivery: the worker is told, in the mailbox

Creating a review appends one line to the reviewed worker's
mailbox file (`team/mailbox/<owner>.jsonl`) — the file-based
version of "send the comment back to the agent". The line
carries ONLY the review id, the verdict word, and a pointer to
the record file — no reviewer free text at all — so it can never
trip the imperative-word scan `validate.py` runs on the mailbox:
the verdict word is `accepted` / `changes-requested`, never the
bare word "approve" (the `\bapprove\b` pattern would FAIL the
push for a human reviewer), and a review note containing a URL
can never leak into the mailbox line. The worker reads the notes
in `team/reviews/<id>.json`. When `require_signatures` is on and
the reviewer is human, the delivery line MUST be signed (`--key`
required — same scheme as `mailbox.py sign`, namespace
`theroster-mailbox`); an unsigned human delivery line would FAIL
validation, so the review is refused instead of half-delivered.
An agent reviewer needs no sig (their commit signature binds the
record).

### Effect: the done-gate, and follow-ups

- **A latest `request-changes` review blocks the PRD
  done-gate.** `prd.py status --to done` and `validate.py`
  FAIL when the latest review on the item — or on any of its
  features, or on any claim bound to the item — is
  `request-changes`. "Latest" is by `created_at`, then id. A
  newer `approve` review on the same subject clears it (the
  worker fixed the notes and the reviewer re-read). A done item
  with a latest `request-changes` review FAILs validation too
  (defense in depth for a hand-written violation).
- **A `request-changes` review re-opens work as a follow-up
  claim.** The reviewed claim stays `done` (history); the worker
  creates a NEW claim linked with `claim.py claim --review
  <review-id>`, which validates that the review exists and its
  verdict is `request-changes` (only a `request-changes` review
  takes a follow-up) and records `review_id` on the claim.
  `reviews.py list` shows follow-ups by scanning claims for
  `review_id`.
- **A review that changes a status is an event.** Creating a
  review appends a `review_created` event; a gate resolution
  that cites a review appends `gate_resolved` with the review
  id. No status changes silently.

## 5. SKILL.md — when to use each, and when NOT to

- **Fan-out:** use only for high-uncertainty work (several valid
  fixes, several defensible architectures). Do NOT use for
  routine work, anything with one right answer, or anything the
  registry already answers with a stable feature. Cost first:
  ×N tokens, ×N worktrees, ×N subscriptions.
- **Gates:** use when a task genuinely cannot proceed without a
  named decision (merge the winner or keep both? which API
  shape? ship or hold?). Do NOT gate routine judgment calls —
  a gate for every decision is a team that cannot move. A gate
  is a question, not a status report.
- **Receipts:** always — `done` files one, no exceptions. A
  receipt is not liveness: it tells you what happened after the
  fact, it does not tell you a worker died mid-task (that is the
  heartbeat's job, 30 minutes + stalled marking).
- **Reviews:** use when the reviewer and the worker are
  different agents (or a human reviewing an agent) and the
  feedback must survive the session. Small teams that already
  review in PRs may not need a separate review record — the
  promote reviewer rule already covers stable promotion. Do NOT
  review your own work.

## 6. Integration — the new records under the old gates

`team_common.team_dir_of()` gains the four new subdirs
(`fanout`, `gates`, `receipts`, `reviews`) so the Dziatkovskii
redirect and the worktree-mutation guard apply to them.

`validate.py` loads all four new record types (`load_all`) and:

- validates each type's schema + references (same sections as
  `fanout.py`/`gates.py`/`receipts.py`/`reviews.py` `check` —
  the per-script `check` is the single source of the rules,
  `validate.py` calls the shared check functions);
- enforces the gate binding (§2) and the review done-gate (§4);
- extends the push-range rules: `TEAM_PREFIXES` and the
  deletion-protection list gain the four new dirs, so a deleted
  fan-out group / gate / receipt / review FAILS like any deleted
  record. The ownership and signature blocks read the actor per
  record type — fan-out: `created_by` (or `decided_by` when
  decided, `cancelled_by` when cancelled); gate: `created_by`
  (or `resolved_by` / `waived_by`); receipt: `done_by`; review:
  `reviewer`. A commit touching a new record type is signed by
  that actor's key when `require_signatures` is on, exactly like
  a claim or feature commit. (The old code read
  `owner_id or id` — for the new types `id` is the record id,
  not a person, so a per-type mapping is required; using the
  record id as the actor would fail the one-owner rule on every
  push that touches a new record.)
- extends event validation: `fanout_id` / `gate_id` /
  `review_id` on a NEW event line must reference a record that
  exists (same rule as `task_id` / `feature_id`).
- extends the secret/PII scan's free-text fields with `note`,
  `question`, `resolution`, `prompt` (the new records' text).

`rebuild_index.py` lists all four new types in
`team/index.json` (id + status + subject, sorted).

`doctor.py` gains check 11: it runs `fanout.py check`,
`gates.py check`, `receipts.py check`, `reviews.py check`
(when the scripts exist) and FAILs on any failure — the new
records are checked at session start, not only at push time.
The version check (check 4) and the script-compile check
(check 5) pick up the new scripts automatically.

No new config knobs. Fan-out, gates, receipts, and reviews are
all opt-in by use: a team that never creates a group, a gate,
or a review pays nothing and changes nothing. Receipts are the
one behavioural change that applies to every team: `claim.py
done` now requires `--outcome` + `--summary`.

Bonus fix (found by the v2.6 smoke test, not by design): the
starter `team/mailbox/assistant.jsonl` ended without a trailing
newline, so the first appended line (a review delivery)
concatenated onto line 1 and corrupted it. New
`team_common.append_jsonl()` / `append_text_lines()`
(newline-safe appends) are now used by `append_event`,
`mailbox.py sign`, the review delivery, and `archive_events.py`;
the starter file itself now ends with `\n`.

## 7. Honest limits (what this does NOT do)

- **No live supervision.** A receipt tells you what happened;
  a gate blocks at the next check; a review is read at the next
  session. Nothing here notices a dead worker in minutes — that
  needs the server (the premium ladder), not a file tweak.
- **No merge decision automation.** `fanout.py compare` is a
  scorecard (receipts + diffstats side by side). Picking the
  winner is a human or coordinator judgment call; the script
  records the decision, it does not make it. There is no
  per-hunk cherry-pick (Orca's merge worktree) — that is a UI,
  and TheRoster has none.
- **A receipt is a claim of completion, not proof of it.** A
  worker can file `succeeded` for broken work. The review is
  the check of the receipt, and the review is only as good as
  the reviewer reading the diff.
- **A gate is only as strong as the check before the push.**
  A worker who never runs `validate.py` and pushes with
  `--no-verify` bypasses the local gate; the CI twin is the
  real gate, as with every other rule in this skill.
- **Signatures bind a record to a key, not to a human.**
  Same limit as v2.4: verification proves the key on the roster
  signed it, not who holds the private key.
- **Fan-out multiplies cost by N, always.** There is no
  deduplication across members: five members can each build the
  same helper five ways, and the four losers' tokens are spent
  whether or not their diffs were useful. That is the price of
  the comparison, and the runbook says so before anything else.
