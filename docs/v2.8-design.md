# v2.8.0 design — Graphyfy: peta kode + roster (team/graph.json)

Roster bilang SIAPA, klaim bilang SIAPA LAGI NGAPAIN, registry bilang
APA YANG SUDAH ADA — tapi tidak ada yang bilang file-nya DI MANA,
SEBERAPA BESAR, dan SIAPA PEMILIKNYA. Agent yang butuh satu file
membaca seluruh repo untuk menemukannya. Graphyfy adalah lapisan
keempat: sebuah peta, `team/graph.json`, yang ditanya agent — bukan
dibaca semua file. Rilis ini memasukkannya ke skill sebagai file
+ git (bukan server), dengan ambang TERUKUR dan gate kesegaran di
`validate.py`. Full design: dokumen ini. Evidence:
`simulations/v2.8.0-evidence.md`.

## 1. Apa yang dibangun

- **Script baru `skills/team-roster/scripts/graph.py`** (stdlib saja,
  adaptasi dari Graphyfy v0.1 di
  `~/workspace/goals/graphyfy-code-graph-with-team-roster/`):
  `build` / `check` / `query`. Tiap file mendapat satu record: `path`,
  `lines`, `bytes`, `tokens_est` (chars/4), `language`, `parsed`
  (Python saja), `symbols` (fungsi/kelas + baris definisi), `links`
  (import yang ter-resolve), `links_unresolved`, `used_by`, `owner` +
  `owner_source` (dari klaim aktif, lalu fitur; "unassigned" kalau
  tidak ada yang mengklaim), `tracked`. Header: `generated_at` +
  `commit_sha` — label "terakhir diketahui" di tiap graph dan tiap
  hasil query.
- **Lokasi: `team/graph.json`, ikut ke-commit** (keputusan Rian
  22 Nov 02:38). Yang di-commit cukup satu file itu — shard per
  direktori hanya ditulis kalau `--shards-dir` diminta eksplisit.
- **Gate di `validate.py` + `doctor.py`** (check 12): keduanya
  memanggil satu fungsi bersama, `graph.check_graph()` — jadi doctor
  dan validate tidak akan pernah tidak sepakat tentang graph.
- **SKILL.md**: bagian "Graphyfy (v2.8)", satu pointer di langkah 4,
  frontmatter → 2.8.0. README: ikon tesseract + deskripsi pendek +
  FAQ collapsible (lihat §5).

## 2. Ambang TERUKUR — bukan tebakan

Keputusan Rian 22 Nov 02:35: ambang harus ditentukan dari hemat
context/token, diukur bukan ditebak. Pengukuran lokal
(`evidence/threshold-measurement.md`, 8 repo, 3–225 file, 238–156.389
baris) DITAMBAH uji repo publik GitHub (Rian 22 Nov 02:54;
`evidence/threshold-github-measurement.md`, 5 repo: tokenize-rt,
retrying, escape-string-regexp, express, requests — clone shallow,
read-only):

- Di bawah ambang **iff file < 5 DAN baris < 500 (AND, bukan OR)**.
  Tebakan lama (10 file ATAU 1.000 baris) DITOLAK data: repo 16 file /
  355 baris masih hemat 74,4%, repo 12 file / 1.098 baris hemat 92,0%.
- Ambang BERTAHAN di GitHub: repo dekat pita (tokenize-rt 14 file /
  852 baris, retrying 12 / 1.303) hemat baterai 84–88%, requests
  (97 file) 95,7%. Tidak ada repo GitHub di atas ambang yang kalah.
- Mengejutkan: graph menang token di SEMUA repo Python yang diukur
  (74,4%–99,0% lokal; 84,5%–95,7% GitHub). Titik balik token murni
  bukan di ukuran repo, tapi per-file: lokal ~140–190 token, GitHub
  ~210–225 token, **gabungan ~140–230 token** (~20–30 baris) — file
  yang lebih kecil dari itu record-nya lebih mahal dari file-nya
  sendiri. Di GitHub efeknya lebih tajam (16 dari 47 file .py, 34%,
  record-nya lebih mahal — lokal 2 dari 73, 3%) karena test suite
  repo GitHub penuh file mungil (`__init__.py` kosong dan
  kawan-kawan). Baterai tetap menang karena pertanyaan menyerang
  file besar — tapi pola "query semua file satu-satu" akan kalah.
- TIDAK ADA repo GitHub yang jatuh ketat di bawah ambang — repo
  GitHub selalu membawa file metadata (README, LICENSE, package.json,
  CI), jadi kotak <5 file / <500 baris hampir tidak ada di dunia
  nyata. Pita 5–10 file / 500–1.000 baris tetap belum terukur ketat
  (9 repo kandidat dicoba, tidak satu pun mendarat di sana); yang
  terukur adalah tepat di luarnya (12–15 file, 852–1.303 baris), dan
  di sana graph menang. Titik lokal di bawah ambang (freelance, 3
  file / 238 baris) tetap satu-satunya titik di bawah.
- Di bawah ambang, graph opsional: skill menyuruh baca langsung.
  Alasannya bukan cuma token — di bawah ~500 baris, hemat absolut
  per batch pertanyaan cuma ~2.000 token sementara repo-nya muat
  dalam satu baca, dan graph menambah biaya tetap (langkah build,
  risiko basi, noise diff `team/graph.json`, konflik merge).
- Repo non-Python: graph MENJAWAB pertanyaan ukuran/dir dengan hemat
  besar (express: J1 file terbesar 98,1%, J2 direktori `test/` 92,4%)
  — tapi NOL untuk simbol/links/owner (tidak ada parser JS). Di repo
  mungil (escape-string-regexp, 11 file / 148 baris) SEMUA file kode
  kalah lawan record-nya — contoh paling murni kenapa ambang ada.

Ambang adalah **konstanta yang didokumentasikan di `graph.py`**
(`THRESHOLD_FILES = 5`, `THRESHOLD_LINES = 500`), bukan knob config —
tidak ada di `team/config.json`. Kalau pengukuran baru mengubahnya,
yang berubah adalah angka di sini + design note, bukan knob.
Alasan: ambang adalah fakta hasil ukur, bukan preferensi tim.
Fungsi murni `graph.below_threshold(n_files, total_lines)` adalah
satu sumber kebenaran aturan ini — dikunci skenario s13 [C4]:
(4, 400) di bawah; (16, 355) di atas; batas (5, 499) dan (4, 500)
di atas; (4, 499) di bawah.

Gate ambang di `check_graph` (repo tanpa graph):

- Di bawah ambang → OK diam-diam (bukan FAIL, bukan warning).
- Di atas ambang tanpa graph → WARNING (bukan FAIL) + perintah
  build. Tim lama yang belum membangun graph tidak di-brick —
  yang hilang hanya peta, bukan kebenaran. Ini keputusan sadar:
  v2.8.0 tidak boleh mem-brick push pertama sebuah tim yang
  upgrade dari v2.7.0.
- Penghitungan ambang itu murah: `count_for_threshold` menghitung
  baris HANYA kalau file < 5 (karena AND: repo dengan >= 5 file
  sudah pasti di atas ambang apa pun jumlah barisnya) — jadi
  `validate.py` tidak membaca isi repo di tiap push.

Yang belum terukur (jujur): pita 5–10 file / 500–1.000 baris dan
repo non-Python — tidak ada repo sampel di sana. Rian meminta uji
repo publik GitHub untuk itu (22 Nov 02:54) — belum dikerjakan,
dicatat di evidence sebagai pekerjaan berikut, bukan bagian v2.8.0.

## 3. Kesegaran — aturan diff, bukan commit_sha == HEAD

Spesifikasi awal (keputusan Rian 22 Nov 02:39): "kalau `commit_sha`
graph != HEAD sekarang, validate FAIL keras". Aturan literal itu
**tidak bisa bekerja untuk graph yang ikut ke-commit** — dan
spesifikasi s13 sendiri menuntut "graph ikut ke-commit di
team/graph.json" sebagai keadaan akhir yang LOLOS:

- Graph dibangun di HEAD C, mencatat `commit_sha = C`.
- Commit graph itu sendiri menggerakkan HEAD ke C' — graph yang
  baru saja di-commit langsung "basi" menurut aturan literal.
  Membangun ulang dan commit lagi hanya mengulang regresi yang sama:
  graph tidak pernah bisa segar setelah di-commit.

Perbaikan yang mempertahankan MAKSUD spesifikasi (peta yang bohong
harus FAIL keras) sambil membuat workflow-nya mungkin:

> **Graph segar iff tidak ada file yang dipetakan berubah sejak
> `commit_sha`.** Diuji dengan
> `git diff --name-only <commit_sha> HEAD -- . ':!team/graph.json'
> ':!team/shards'`.

- Commit yang hanya mengubah `team/graph.json` (dan `team/shards/`)
  TIDAK membuat graph basi — graph tidak memetakan dirinya sendiri,
  jadi peta itu masih benar. Ini dibuktikan s13 §D: validate +
  `graph.py check` LOLOS setelah commit graph saja.
- Commit kerja apa pun (satu file yang dipetakan berubah) membuat
  graph basi → `validate.py` FAIL dengan perintah regenerate,
  `graph.py check` FAIL "GRAPH BASI". Dibuktikan s13 §B.
- `commit_sha == HEAD` tetap segar (diff kosong) — kasus build
  yang belum di-commit.
- Kalau base commit tidak ada di clone ini (shallow clone) atau
  repo bukan git → "unverifiable" → WARNING, bukan FAIL (validate),
  FAIL di `graph.py check` CLI (perintah langsung: "cek graph ini"
  — yang tidak bisa dipastikan tidak boleh dibilang segar).
- Working tree kotor hanya WARNING: graph cocok dengan HEAD, tapi
  disk sudah bergerak sesudah commit — jawaban graph =
  "terakhir diketahui", bukan "sekarang".

Satu sumber kebenaran: `graph.graph_freshness()` dipakai `check`
CLI, `check_graph` (validate/doctor), dan query (`fresh_vs_head`).
Tidak ada dua implementasi aturan yang bisa berpisah.

Urutan kerja yang benar (ditulis di SKILL.md): commit kerja →
build graph → commit graph sendiri → push. Graph yang di-commit
BERSAMA commit kerja adalah graph basi — ia dibangun sebelum commit
itu, jadi tidak mendeskripsikan isi baru commit itu. `validate.py`
akan menangkapnya (diff mencakup file kerja).

## 4. Keputusan desain lain (dan batas jujur)

- **`.gitignore` dihormati.** `collect_files` memakai
  `git ls-files --cached --others --exclude-standard` (tracked +
  untracked-yang-tidak-di-ignore). Fallback `os.walk` kalau bukan
  repo git — dicatat di header graph (`gitignore_applied`).
  Bukti s13 [A2]: `team/index.json` (generated + gitignored) TIDAK
  masuk graph.
- **Bug `.github` (temuan uji GitHub, DIPERBAIKI di v2.8.0).**
  `build_graph.py` v0.1 memakai `d.startswith(".git")` untuk
  melewati direktori — itu ikut melewatkan `.github`: requests
  kehilangan 19 file (workflow + template issue + kebijakan),
  tokenize-rt 1 file. v2.8.0 memakai pencocokan eksak (`SKIP_DIRS`
  berisi `".git"`; tidak ada `startswith` lagi) di KEDUA jalur
  (`ls-files` dan fallback `os.walk`). Dikunci s13 [A2b] (jalur
  git) dan [A2c] (jalur fallback non-git): repo yang punya
  `.github/` harus tetap memetakan file-file di dalamnya.
- **Konstanta ambang lama (temuan uji GitHub, DIPERBAIKI di
  v2.8.0).** `build_graph.py` v0.1 masih memakai `THRESHOLD_FILES =
  10` / `THRESHOLD_LINES = 1000` dan `or` — `threshold_note`-nya
  menyebut repo di atas ambang baru sebagai "di bawah ambang".
  v2.8.0: 5 file / 500 baris, AND, di `below_threshold()` +
  `threshold_note`. Dikunci s13 [C3]/[C4].
- **Graph tidak memetakan dirinya sendiri.** `build` mengecualikan
  file `--out` dan `--shards-dir` dari daftar file — kalau tidak,
  tiap build berikutnya memetakan graph/shard versi lama dan
  ukurannya tumbuh sendiri.
- **Tidak ada isi file, tidak ada secret.** Metadata saja; `.env`,
  `*.pem`, `*.key`, `*credentials*`, `*secret*` tidak pernah masuk
  graph (0 di semua pengukuran). Jalur absolut repo tercatat di
  header (`repo`) — itu metadata lokal mesin pembangun, bukan
  secret; tim yang peduli bisa strip field itu (tidak dipakai
  `validate.py`/`doctor.py` — keduanya menurunkan repo dari
  `team_dir`).
- **Owner = klaim AKTIF (termasuk yang kedaluwarsa/stealable).**
  Graph menjawab "tanya siapa" — siapa yang terakhir mengklaim
  file itu. Apakah file itu TERKUNCI sekarang diputuskan
  `claim.py check`, bukan graph. (v0.1 sudah begitu; dipertahankan
  dan didokumentasikan, bukan diubah diam-diam.)
- **Hanya Python yang di-parse.** Bahasa lain dicatat unparsed
  dengan jujur (case 19). Resolusi import best-effort (basename
  ambigu gagal — dicatat `links_unresolved`, bukan ditebak).
- **Graph adalah snapshot, bukan live.** Tanpa regenerate ia basi —
  tapi sekarang basi itu TERDETEKSI, bukan diam-diam. Graph tidak
  membuktikan perilaku — seperti line citation, ia memverifikasi
  LOKASI (simbol ada di file:baris), bukan deskripsi.
- **Graph bukan record `team/` yang dilindungi.** `team/graph.json`
  sengaja TIDAK masuk `TEAM_PREFIXES` / deletion-protection
  `validate.py`: ia data turunan yang bisa di-build ulang — menghapusnya
  bisa dipulihkan dengan satu perintah, tidak seperti roster/klaim.
  Perubahan graph juga tidak butuh atribusi pemilik (yang menulis
  hanya generator, bukan agent).
- **Tidak ada knob baru.** Satu-satunya "angka" adalah konstanta
  ambang (§2). `doctor.py` check 12 memakai gate yang sama dengan
  validate — FAIL kalau graph basi di awal sesi (memulai kerja
  dengan peta bohong adalah persis mode gagalnya).

## 6. Masih belum diperbaiki / tidak diuji

- Pita ambang 5–10 file / 500–1.000 baris tetap belum terukur ketat
  (tidak ada repo GitHub yang mendarat di sana); kotak di bawah
  ambang belum ada datanya di GitHub — satu-satunya titik di bawah
  tetap repo lokal (freelance, 3 file / 238 baris).
- **v0.2 (catatan, JANGAN dibangun di v2.8.0): record ringkas.**
  Record yang menyimpan daftar simbol lengkap menjadi gemuk di file
  dengan banyak simbol — bukti: record `tests/test_requests.py` =
  **9.223 token untuk 301 simbol** (Q2 cuma hemat 66,0%;
  `test_retrying.py` 1.763 token / 62 simbol, Q2 cuma 55,2%).
  Record ringkas (jumlah simbol, bukan daftar lengkap) akan
  menggeser titik balik per-file ke bawah — tapi itu mengubah isi
  record dan butuh pengukuran ulang, jadi ditunda ke v0.2.
- Repo non-Python: hanya dicatat unparsed — hematnya berbeda (hanya
  ukuran/dir, tanpa simbol/links/owner).
- Graph tidak menjawab error env/config/DB (case 13) — tidak ada
  jawaban graph untuk error yang tidak ada di kode.
- `query --dir` / `--symbol` membaca `graph.json` utuh ke memori —
  untuk repo raksasa, shard-lah yang seharusnya dibaca (shard
  per-direktori sudah bisa ditulis dengan `--shards-dir`, tapi
  `query` belum memakai shard file).
- Live presence / verifikasi live via bridge (analogi dunia kaca) —
  tetap server-shaped, bukan bagian skill file+git.
- Semua "Still not fixed" v2.7.0 tetap berlaku (lihat CHANGELOG
  v2.7.0) — v2.8.0 tidak menutup satu pun dari daftar itu.
