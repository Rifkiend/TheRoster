  (`"STOP semua kerja hari ini. Jangan klaim apa pun. Lepas klaim t-001

## What is NOT closed by v2.4.0 (honest list)

These were the ranked-below items in the rare-case report — explicitly
NOT in v2.4.0 scope, still queued:

- Deletion detection in the push range (case 2, partly).
- Trailer enforcement (case 2) — only meaningful after signed identity;
  now possible, still unbuilt.
- Events-content validation (case 2).
- Clock-skew FAIL gate (case 3) — stealability still follows wall-clock.
- Ghost-claim auto-release on roster removal (case 4).
- Reject `team/` paths in claims (case 5, hardening).
- Dependency cycle detection (case 6).
- Duplicate display names FAIL (case 9, names).
- Last-known-main-SHA force-push detection (case 8, partly).
- Cross-repo board / live presence / atomic claims (case 11, case 3
  presence) — need a server; do not fake with files.

## What was NOT tested

- `created_seq` under TRUE concurrency: two agents creating claims at
  the same moment can compute the same number (a file is not an atomic
  counter). The push fence (first push wins) adjudicates; this was
  documented, not demonstrated — demonstrating it needs two agents
  racing, not one script.
- A real second machine: cross-machine worktree/signature behaviour is
  covered only by skip+note (E7) and by the design (keys travel in the
  roster, verification is local `git verify-commit`).
- git < 2.38 on a real machine (merge-tree fallback tested via shim only,
  in the v2.3.0 extreme round — unchanged by v2.4.0).
- Semantic conflicts (a clean merge that still breaks behaviour).
- Scale beyond 50/300/50 in this rerun (original: 100/1000/100).
- The mailbox `sig` field: documented in SKILL.md, not enforced.
- Real human key management: key generation, storage, rotation, and
  revocation are the team's operational job — the skill only verifies
  the key that is on the roster.
